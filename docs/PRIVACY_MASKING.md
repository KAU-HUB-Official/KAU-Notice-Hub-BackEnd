# 개인 식별자 마스킹

공지의 학번·이름·연락처를 **본문, 검색 인덱스, LLM 입력** 세 곳에서 가린다. 구현은
`app/privacy.py`이고 전부 정규식과 문자열 처리다. LLM은 쓰지 않는다.

## 목적

원문은 이미 학교 사이트에 공개되어 있다. 문제는 우리가 성격을 바꾼 부분이다.
학교는 공지를 68개 게시판에 나눠 올리고 시간이 지나면 묻히지만, 우리는 3년치를
한 곳에 모아 학번을 전문 검색 대상으로 만들었다. 실제로 학번 하나를 검색하면
서로 다른 두 공지가 이어져, 한 학생이 특정 교육 수강자이면서 특정 학기 졸업사정
대상자라는 사실이 한 번에 드러났다.

검색 경로를 막는 것이 1차 목적이고, 유출 위험을 줄이기 위해 본문 표시까지 함께
가린다.

## 적용 지점

| 위치 | 대상 |
| --- | --- |
| `app/normalize.py` `normalize_notice()` | 사용자에게 렌더되는 공지 본문 (`mask_notice_body()`) |
| `app/search.py` `build_search_text()` | 검색 인덱스. SQLite 적재(`app/ingest.py`)와 JSON 폴백 검색이 함께 쓰는 단일 관문이다 |
| `app/chat_service.py` `build_context()` | RAG 답변 컨텍스트 |
| `app/chat_service.py` `build_rerank_list()` | rerank 입력 |
| `app/chat_service.py` `fallback_answer()` | LLM 미사용 시 노출되는 발췌 |

### 건드리지 않는 것

- **제목**: `build_notice_id()`가 제목으로 공지 ID를 만든다. 제목을 바꾸면 ID가 변해
  사용자가 저장한 북마크가 끊긴다. 본문은 ID 계산에 쓰이지 않아 안전하다.
- **첨부파일**: 파일명과 URL을 그대로 둔다. PDF·HWP·이미지 안의 명단은 텍스트
  마스킹이 닿지 않으므로 여전히 노출된다.
- **공지 날짜, 학년도, 이미지·링크 URL, 마크다운 구조**: 전수 기준으로 1개도 변하지
  않음을 검증했다.

## 마스킹 대상

항상 가린다.

| 대상 | 방식 | 결과 |
| --- | --- | --- |
| 10자리 학번 | 정규식 + 예시값 필터 | `2017121128` → `2017○○○○○○` |
| 학번 바로 뒤 한글 이름 | 가려진 학번을 앵커로 사용 | `심재원` → `심○○` |
| 표의 성명/이름 컬럼 | 헤더에서 컬럼 위치를 찾아 해당 셀만 | `김솔미` → `김○○` |

설정(`PRIVACY_MASK_CONTACTS`, 기본 켜짐)에 따라 연락처도 가린다.

| 대상 | 결과 |
| --- | --- |
| 전화번호 | `02-300-0272` → `02-○○○-○○○○` |
| 이메일 | `cap@kau.ac.kr` → `○○○@kau.ac.kr` |
| 계좌번호 | `우리은행 1005-003-863678` → `우리은행 ○○○○-○○○-○○○○○○` |
| 주민등록번호 | `900101-1234567` → `○○○○○○-○○○○○○○` |

주민등록번호와 생년월일은 전수 스캔 0건이라 실제로는 유입 대비용이다.

## 설정

| 환경변수 | 기본 | 끄면 |
| --- | --- | --- |
| `PRIVACY_MASK_BODY` | `true` | 본문만 원문으로 돌아간다. 검색 인덱스와 LLM 입력은 계속 가려진다 |
| `PRIVACY_MASK_CONTACTS` | `true` | 연락처를 가리지 않는다. 학번과 표 성명 셀만 가린다 |

공지 DB는 크롤링마다 통째로 교체되므로 설정을 바꾸고 다음 적재를 기다리면 된다.
마이그레이션이 필요 없다.

## 연락처를 가리는 이유와 비용

검출된 연락처 4,700여 건은 전수 확인 결과 사실상 전부 부서 업무 연락처
(`문의 : 교육성과관리센터 02-300-0272`)와 학교 법인계좌
(`우리은행 1005-003-863678`)다. 개인 연락처는 78건이고 그마저 대부분 외부
운영사무국 담당자다. 즉 개인정보로서의 위험은 낮다.

그래도 유출 위험을 낮추는 쪽을 기본값으로 택했다. 비용은 두 가지다.

- **공지 상세에서 문의처를 읽을 수 없다.** 사용자는 원문 링크로 가야 한다.
- **챗봇이 문의처를 답하지 못한다.** RAG는 컨텍스트만 근거로 답한다.

받아들이기 어려워지면 `PRIVACY_MASK_CONTACTS=false`로 끈다.

## 설계상 주의할 점

**한글 이름은 단독 정규식으로 잡지 않는다.** `[가-힣]{2,4}\s*학생` 패턴은
`완료한 학생`, `재학생` 같은 일반 표현을 1,932건 오탐했다. 그래서 이름은 반드시
앵커(가려진 학번, 표 성명 컬럼)가 있을 때만 처리한다.

**학번 앞은 보지 않는다.** `기계 2018121173 이휘`처럼 학번 앞은 소속명이 오는
자리다. 그쪽까지 보면 학과명을 이름으로 오탐한다.

**예시값 판정은 좁게 둔다.** 뒤 6자리가 한 숫자로만 채워졌거나 연속 숫자인 경우만
예시로 본다. `숫자 종류가 둘 이하`처럼 넓게 잡으면 `2018121111`(뒤 6자리
`121111`) 같은 실제 학번을 예시로 오판해 그대로 노출된다. 예시값을 몇 개 더
가리는 손해는 검색어 하나가 덜 걸리는 정도지만, 실제 학번을 놓치면 사람이
특정된다.

**표가 살아 있다고 가정하지 않는다.** `normalize_notice()`는 비정형 표를 평문으로
펼치므로 파이프가 사라진다. 학번·실명 195명이 실린 캡스톤 공지가 그 경우이고,
그래서 컬럼 기반 규칙만으로는 최악 케이스를 덮지 못한다. 학번 앵커 규칙이 이
구간을 담당한다.

**마스킹 문자로 `*`를 쓰지 않는다.** 본문도 가리므로 마스킹 결과가 마크다운에
그대로 들어간다. 공지는 굵게를 많이 써서 `**문의 02-300-0272**`가
`**문의 02-***-******`가 되어 강조 파싱이 깨진다(전수 기준 3,870건). `○`는
마크다운에서 의미가 없고, 학교가 이미 `박○영` 형태로 쓰는 글자라 표기도 일관된다.

**전화번호 첫 구분자는 필수다.** 생략을 허용하면 URL 안의 긴 해시
(`?physical=ec8ba6e57d182021049940a24eb87c7b07c19`)를 전화번호로 보고 잘라 링크를
깨뜨린다(전수 기준 80개). 구분자 없는 9~11자리 숫자열 44건을 확인했는데 전부 URL
해시와 파일명이고 실제 전화번호는 없었다.

**표 라인을 재조립할 때 들여쓰기를 보존한다.** 앞 공백을 버리면 원문에 없던 표가
생긴 것처럼 보인다.

것**을 더 촘촘하게 검사한다.

## 남는 한계

- 원문은 학교 사이트에 그대로 공개되어 있다. 마스킹은 보호가 아니라 우리가
  증폭하지 않는다는 뜻이다.
- **명단 상당수는 첨부 PDF·HWP·이미지 안에 있다.** 제목에 `명단`·`합격자`·`선발자`가
  들어간 첨부파일이 150건이고, 우리는 다운로드 주소만 제공하므로 손을 댈 수 없다.
  현재 가장 큰 구멍이다.
- 표가 평문으로 펼쳐지고 이름이 학번보다 앞에 오는 배치는 가리지 못한다. 관측된
  데이터에서 그 배치는 학교가 이미 `조O빈` 형태로 가려 둔 공지들이었다.
- **학번도 성명 컬럼도 없는 실명은 가리지 못한다.** `2026-2 재학생선배 전공설계
  릴레이 토크 운영안내`의 발표자 11명이 `이름(입학년도)` 형태로 남아 있다. 발표자로
  공개 활동하는 학생이라 가리면 공지가 무의미해져, 팀 결정 사항으로 둔다.
